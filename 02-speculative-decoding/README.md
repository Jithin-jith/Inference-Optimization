# Module 02: Speculative Decoding

## 1. Technical Explanation & Mathematical Intuition

Autoregressive LLM generation is fundamentally **memory-bandwidth bound**. For every single token generated by a massive target model $M_{\text{target}}$ (e.g., 70B+ parameters or Gemini Pro), the engine must load all billions of weight parameters from GPU High Bandwidth Memory (HBM) into compute units. Because matrix multiplication arithmetic operations per parameter are minimal during single-token decoding ($B = 1$), the GPU tensor cores sit largely idle while waiting for weights to transfer over the memory bus.

**Speculative Decoding** breaks this memory bandwidth bottleneck by decoupling candidate token proposal from candidate token verification through a dual-model architecture:

1. **Lightweight Draft Model ($M_{\text{draft}}$)**: A small, fast model (e.g., 1B–3B parameters or Gemini Flash) that rapidly drafts a speculative sequence of tokens autoregressively.
2. **Heavy Target Model ($M_{\text{target}}$)**: A high-capacity model (e.g., 70B+ parameters or Gemini 3.1 Pro) that validates all drafted candidate tokens simultaneously in a **single compute-bound parallel forward pass**.

```
                       +-----------------------------------+
                       |   Prompt Context (Input Tokens)   |
                       +-----------------------------------+
                                         |
                                         v
                  +----------------------------------------------+
                  | Draft Model M_draft (Fast Memory Transfer)   |
                  | Autoregressively generates γ draft tokens    |
                  +----------------------------------------------+
                                         |
                       Draft Tokens: [ x1, x2, x3, x4 ]
                                         |
                                         v
                  +----------------------------------------------+
                  | Target Model M_target (Parallel Verification)|
                  | Evaluates [x1, x2, x3, x4, x5] in ONE pass!  |
                  +----------------------------------------------+
                                         |
                                         v
                  +----------------------------------------------+
                  |     Rejection Sampling & Validation Loop     |
                  |  Accept tokens up to first rejection point   |
                  +----------------------------------------------+
                                         |
                       Accepted: [ x1, x2 ] + New Token x3'
```

---

### Algorithmic Execution Steps

1. **Draft Candidate Proposal**:
   The draft model $M_{\text{draft}}$ generates a lookahead sequence of $\gamma$ candidate tokens $x_1, x_2, \dots, x_\gamma$ autoregressively:
   $$x_i \sim P_{\text{draft}}(\cdot \mid x_{<i})$$
   Because $M_{\text{draft}}$ has significantly fewer parameters, loading its weights takes a fraction of the time required by $M_{\text{target}}$.

2. **Parallel Target Model Forward Pass**:
   Instead of generating tokens one by one, the target model $M_{\text{target}}$ processes all $\gamma$ candidate tokens (plus one extra continuation token) concurrently in a single forward pass:
   $$P_{\text{target}}(x_i \mid x_{<i}) \quad \forall i \in \{1, 2, \dots, \gamma + 1\}$$
   Because evaluating multiple prompt tokens in parallel is **compute-bound** (prefill efficiency), verifying $\gamma$ tokens takes nearly the **same wall-clock time** as generating a single token autoregressively!

3. **Rejection Sampling & Distribution Preservation**:
   To guarantee that the final generated output follows the **exact mathematical probability distribution** of $M_{\text{target}}$, candidates are validated sequentially. For candidate token $x_i$, accept with probability:
   $$P(\text{accept}) = \min\left(1, \frac{P_{\text{target}}(x_i)}{P_{\text{draft}}(x_i)}\right)$$
   - If token $x_i$ is **accepted**, move to candidate $x_{i+1}$.
   - If token $x_i$ is **rejected** at index $k$, discard all subsequent candidates ($x_{k+1}, \dots, x_\gamma$) and sample a fresh replacement token $x_k'$ from the adjusted distribution:
     $$P(x_k') = \max\left(0, P_{\text{target}}(x_k) - P_{\text{draft}}(x_k)\right)$$

---

### Speedup Equation & Mathematical Bounds

Let $\gamma$ be the speculative lookahead window size, $\alpha \in [0, 1]$ be the average acceptance rate of draft tokens, $T_{\text{draft}}$ be the single-token decode latency of $M_{\text{draft}}$, and $T_{\text{target}}$ be the forward pass latency of $M_{\text{target}}$.

The expected number of accepted tokens per verification cycle is:
$$\mathbb{E}[\text{accepted}] = \frac{1 - \alpha^{\gamma + 1}}{1 - \alpha}$$

The expected wall-clock speedup factor $S$ is expressed as:
$$S = \frac{\mathbb{E}[\text{accepted}]}{1 + \gamma \cdot \frac{T_{\text{draft}}}{T_{\text{target}}}}$$

When $T_{\text{draft}} \ll T_{\text{target}}$ and $\alpha \to 1$, the speedup factor approaches:
$$S_{\text{max}} \approx 1 + \alpha \cdot \gamma$$

## 2. Detailed Timing & Latency Comparison (With vs. Without Speculative Decoding)

The table below summarizes empirical performance metrics comparing traditional autoregressive decoding against speculative decoding across both self-hosted serving engines (vLLM / PyTorch) and cloud API cascade patterns (Google Gemini API).

| Performance Metric | WITHOUT Speculative Decoding (Direct Target Model) | WITH Speculative Decoding (Draft-Target Cascade) | Impact & Optimization Analysis |
|---|---|---|---|
| **Time-To-First-Token (TTFT)** | **High Latency** (~3.5s – 4.5s on 70B target) | **Ultra-Fast** (~0.4s – 0.6s via draft model) | **6x – 8x TTFT Reduction**: Initial draft content renders almost instantaneously to the user interface. |
| **Inter-Token Latency (ITL)** | **Baseline** (30ms – 60ms per token) | **Accelerated** (10ms – 20ms effective ITL) | **2x – 3x Speedup**: Generates multiple tokens per single target model memory access pass. |
| **End-to-End Latency** | **Slow** (Linear scaling $N \times T_{\text{target}}$) | **Fast** (Reduced cycles $(N / \mathbb{E}[\text{accepted}]) \times T_{\text{target}}$) | **Overall 1.8x – 2.8x Latency Drop** for standard output lengths (250–1000 tokens). |
| **Output Quality / Distribution** | Standard Target Model Quality | **100% Mathematically Identical** to Target Model | **Zero Degradation**: Rejection sampling guarantees exact probability distribution preservation. |
| **GPU Memory (VRAM) Usage** | Target Model VRAM + Target KV-Cache | Target Model VRAM + **Draft Model VRAM + Dual KV-Cache** | Requires extra VRAM (~5%–15% additional memory) to host draft weights and KV cache. |
| **GPU Compute Saturation** | Low (Compute units wait on memory bus) | High (Compute units process $\gamma+1$ tokens in parallel) | Maximizes Tensor Core utilization without changing hardware specs. |

## 3. Architecture & Execution Flow

```
Draft Model (Fast):   [T1] -> [T2] -> [T3] -> [T4] (Generates 4 candidate tokens)
                                 |
                                 v
Target Model (Parallel): Verify [T1, T2, T3, T4] in ONE single forward pass!
                                 |
Validation Check:               [OK] [OK] [FAIL] [DISCARD]
                                 |
Accepted Tokens:               T1, T2 + New Target Token T3' (3 tokens generated in ~1 target step time)
```

## 4. Open-Source vs Proprietary Paradigm

- **Open-Source Serving Engines (vLLM / TensorRT-LLM / PyTorch)**:
  - Speculative decoding is integrated directly into the inference engine KV-cache manager.
  - vLLM supports speculative decoding via CLI flags: `--speculative-model <draft_model_name> --num-speculative-tokens 5`.
  - **Constraint**: Draft model and target model **must use the exact same tokenizer and vocabulary** (e.g., Llama-3-8B draft for Llama-3-70B target).

- **Proprietary APIs (Google Gemini API)**:
  - Google Gemini serving infrastructure utilizes internal speculative draft engines (e.g., Gemini 2.5 Flash serving as a speculative draft engine for Gemini Pro / Gemini 3.1 Pro).
  - API developers can also implement **Client-Side Draft-Target Cascading** (`proprietary_gemini.py`):
    1. Send prompt to `gemini-2.5-flash` at low temperature (0.1 - 0.2) to obtain an immediate draft (~200ms TTFT).
    2. Pass draft to `gemini-3.1-pro-preview` for single-pass verification, code execution sanity, and mathematical validation.

## 5. When to Use Speculative Decoding

> [!TIP]
> Speculative decoding delivers maximum speedup when inference is memory-bandwidth bound and draft token acceptance is high.

### Ideal Use Cases:
1. **Low Batch Size ($B = 1$ to $B = 4$) Online Inference**:
   When serving real-time user requests (chat interfaces, IDE code autocompletion), GPU memory bandwidth is the primary bottleneck. Speculative decoding increases tensor core compute saturation.
2. **Massive Target Models with Small Draft Models**:
   Pairing 70B or 405B parameter target models with 1B–3B draft models yields dramatic latency speedups because $T_{\text{draft}} \ll T_{\text{target}}$.
3. **Structured & Predictable Output Domains ($\alpha > 70\%$)**:
   - **Code Generation & Boilerplate**: High syntactic predictability (e.g., Python `def`, `import`, SQL schemas).
   - **Structured JSON / Schema Parsing**: High acceptance rates due to constrained grammar.
   - **Summarization & Translation**: Strong contextual overlap between draft and target models.
4. **Low Temperature Sampling ($T \le 0.2$)**:
   Greedy decoding or low-temperature sampling aligns draft probabilities closely with target model logits, maximizing candidate acceptance $\alpha$.
5. **Interactive Applications Demanding Low TTFT**:
   Using client-side draft-target cascading renders an initial actionable draft to the end-user in <500ms while target verification completes in the background.

## 6. When NOT to Use Speculative Decoding

> [!WARNING]
> Speculative decoding can decrease efficiency or degrade latency under compute-bound or low-acceptance conditions.

### Do NOT Use Speculative Decoding When:
1. **High Batch Size / High Throughput Offline Serving ($B \ge 32$)**:
   At high batch sizes, GPU tensor cores are already 100% compute-saturated by standard prefill/decode operations. Adding a draft model introduces additional overhead without latency reduction.
2. **Low Acceptance Rate Domains ($\alpha < 40\%$)**:
   - **High-Temperature Creative Writing ($T \ge 1.0$)**: High entropy randomness causes frequent candidate rejections, wasting draft compute cycles.
   - **Domain Mismatch**: If the draft model is fine-tuned on code but the target model is used for medical QA, low acceptance will slow down inference.
3. **VRAM-Constrained Hardware Environments**:
   If GPU VRAM is tight, allocating memory for the draft model's parameters and second KV-cache will decrease max context length or force offloading.
4. **Target Models That Are Already Small ($<3\text{B}$ Parameters)**:
   When the target model is already fast and lightweight, the relative ratio $T_{\text{draft}} / T_{\text{target}}$ approaches 1, eliminating speculative advantage.
5. **Short Generation Requests ($<20$ Tokens)**:
   For tiny prompt completions, the overhead of draft initialization and KV-cache management cancels out potential token generation savings.

## 7. Important Notes & Production Gotchas

> [!IMPORTANT]
> Keep these critical production rules in mind when deploying speculative decoding pipelines:

1. **Tokenizer & Vocabulary Uniformity**:
   In open-source frameworks (vLLM, TensorRT-LLM), draft and target models **must share identical vocabulary token IDs**. Token ID mismatch will produce index corruption during rejection sampling.
2. **Tuning the Speculative Lookahead Window ($\gamma$)**:
   - Setting $\gamma$ too low ($\gamma = 1, 2$) limits max speedup potential.
   - Setting $\gamma$ too high ($\gamma = 8, 10$) wastes draft compute when candidates are rejected early.
   - **Optimal Production Default**: $\gamma \in [3, 5]$.
3. **Rejection Sampling Temperature Matching**:
   Ensure temperature and top-$p$ settings are identical across both draft and target sampling configurations to preserve target probability distributions.
4. **Cloud API Rate Limits & Cost Dynamics**:
   In client-side draft-target cascading (e.g., Google Gemini), issuing two API calls (Flash + Pro) increases total API token usage. Ensure cost trade-offs align with TTFT latency requirements.
